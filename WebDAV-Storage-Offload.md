## 1. Что делает плагин

**WebDAV Storage Offload** автоматически выгружает медиафайлы WordPress (изображения, PDF, документы) в удалённое WebDAV-хранилище (Nextcloud, ownCloud, Яндекс.Диск, Mail.ru, Synology, Box, локальный сервер и т.д.). После выгрузки файлы можно удалить с локального сервера, экономя место.

### Возможности

- **Прозрачная выгрузка** — при загрузке файла через медиабиблиотеку он автоматически отправляется в WebDAV, WordPress получает публичную ссылку.
- **REST-прокси** — если у WebDAV нет публичного доступа, файлы отдаются через `/wp-json/webdav-storage/v1/file/...` (с кэшем и поддержкой Range для видео).
- **Пакетная выгрузка** — кнопка в админке прогоняет все существующие медиафайлы через AJAX (по одному, чтобы не словить таймаут).
- **Удаление локальных копий** — опция «удалять после выгрузки» экономит место на диске.
- **Автоуникализация имён** — если в WebDAV уже есть файл с таким именем, добавляется суффикс `-1`, `-2` и т.д.
- **Шифрование пароля** — хранится в БД в зашифрованном виде (AES-256-CBC, ключ из `wp_salt('auth')`).
- **Логирование** — отладочный лог + список последних 20 ошибок в админке.
- **Работает с curl** — при наличии curl использует потоковую загрузку (streaming upload) без загрузки файла в память.

## 2. Требования

| Параметр | Минимум | Рекомендуется |
|---|---|---|
| PHP | 7.4 | 8.0+ |
| WordPress | 5.5 | 6.0+ |
| **Расширение curl** | — (fallback на `wp_remote_request`) | ✅ для стриминга больших файлов |
| **openssl** | — (fallback на base64) | ✅ для шифрования пароля |
| **Права на WebDAV** | — | запись + чтение + удаление |
| **Лимит памяти** | 128MB | 256MB+ |
| **`max_execution_time`** | 30 сек | 300+ сек (для больших файлов) |

### 2.1. Как проверить, что есть curl и openssl

**Инструменты → Здоровье сайта → Сведения → Сервер** — там указано.

Или в `wp-content/debug.php` временно:
```php
var_dump(function_exists('curl_init'));   // true — curl есть
var_dump(function_exists('openssl_encrypt')); // true — openssl есть
```

## 3. Установка и активация

### 3.1. Установка

**Вариант А — через админку:**

1. Скачать ZIP с плагином.
2. **Плагины → Добавить новый → Загрузить плагин** → выбрать ZIP → **Установить** → **Активировать**.

**Вариант Б — через FTP:**

1. Распаковать архив в `/wp-content/plugins/webdav-storage-offload/`.
2. Админка → **Плагины** → найти **«WebDAV Storage Offload»** → **Активировать**.

### 3.2. После активации

- В админке появится пункт **Настройки → WebDAV Storage**.
- Плагин **не начнёт** выгружать файлы, пока не включён чекбокс **«Включить выгрузку»**.

### 3.3. Структура плагина

```
webdav-storage-offload/
├── webdav-storage-offload.php   # единственный файл (класс + клиент)
└── (лог)  /wp-content/uploads/webdav-offload-debug.log
```

## 4. Быстрый старт

За 5 минут:

1. **Настройки → WebDAV Storage**.
2. Заполнить:
   - **WebDAV URL**: `https://cloud.example.com/remote.php/dav/files/USER/wordpress`
   - **Логин** / **Пароль** от WebDAV-аккаунта.
   - **Публичный URL**: `https://cloud.example.com/s/USER` (если есть публичный доступ) или оставить пустым — тогда используется REST-прокси.
3. Нажать **«Проверить подключение»** → должно появиться «✓ Подключение успешно».
4. Поставить галочку **«Включить выгрузку»** → **Сохранить**.
5. Загрузить тестовую картинку через **Медиафайлы → Добавить** — она уйдёт в WebDAV.
6. Проверить в WebDAV-клиенте, что файл появился.
7. Если нужно перенести всё старое — **Настройки → WebDAV Storage → «Выгрузить существующие медиафайлы»**.

## 5. Настройки плагина

Все настройки — **Настройки → WebDAV Storage**.

### 5.1. Включить выгрузку

- `enabled` (checkbox)
- **Не включайте**, пока не проверили подключение кнопкой «Проверить подключение». Иначе новые загрузки могут «сломаться» из-за недоступного WebDAV.

### 5.2. WebDAV URL

- `url` (text)
- Полный URL папки на WebDAV-сервере, **куда** будут складываться файлы.
- **Примеры:**
  - **Nextcloud:** `https://cloud.example.com/remote.php/dav/files/USERNAME/wordpress`
  - **ownCloud:** `https://cloud.example.com/remote.php/webdav/wordpress`
  - **Яндекс.Диск:** `https://webdav.yandex.ru/wordpress`
  - **Box:** `https://dav.box.com/dav/wordpress`
  - **Synology:** `https://nas.local:5006/wordpress`
  - **Локальный сервер:** `http://192.168.1.10/dav/wordpress`
- **Не добавляйте** слэш в конце — плагин сам обработает.
- Папка должна **существовать** либо быть создаваемой (плагин делает `MKCOL` при необходимости).

### 5.3. Логин и пароль

- `username` (text)
- `password` (password, шифруется AES-256-CBC при сохранении)
- Используются для **Basic Authentication** в WebDAV.
- Если у вас **Nextcloud** — лучше создать **app password** (Настройки → Безопасность → Пароли приложений), а не использовать основной пароль.
- Поле пароля в форме **всегда пустое** — оставьте пустым, чтобы сохранить текущий. Введите новый, чтобы заменить.

### 5.4. Публичный URL

- `public_url` (text)
- **Необязательно.** Прямой URL, по которому файлы доступны без авторизации (CDN, публичная папка Nextcloud и т.д.).
- Если задан:
  - WordPress подставляет его в `upload_dir['baseurl']` — все ссылки в контенте будут вести туда.
  - REST-прокси не используется.
- Если **не задан**:
  - Ссылки идут через `/wp-json/webdav-storage/v1/file/...` — плагин сам стримит файл из WebDAV (поддерживает Range, ETag, кэш).
- **Совет:** для production всегда лучше иметь прямой публичный URL — прокси даёт лишнюю нагрузку на сервер.

### 5.5. Удаление локальных файлов

- `delete_local` (checkbox)
- Если включено — после успешной выгрузки файл **удаляется** с диска сервера.
- ⚠️ **Внимание:** включите, только когда убедитесь, что WebDAV-копии создаются корректно.
- Удаляются также все размеры (`thumbnail`, `medium`, `large` и т.д.).

### 5.6. Проверка SSL

- `sslverify` (checkbox, по умолчанию **включено**)
- Отключите **только** для самоподписанных сертификатов на тестовом стенде.
- На production **всегда включено**.

### 5.7. Уникальные имена файлов

- `unique_names` (checkbox, по умолчанию **включено**)
- Если в WebDAV уже есть файл `photo.jpg` — при загрузке нового будет создан `photo-1.jpg`, `photo-2.jpg` и т.д.
- Отключите, если уверены, что имена не пересекаются (например, используются UUID).

### 5.8. Режим отладки

- `debug_mode` (checkbox)
- Включает запись лога в `/wp-content/uploads/webdav-offload-debug.log`.
- Ошибки в лог пишутся **всегда** в `error_log` PHP (без отдельного файла), но в файл — только при включённой отладке.

## 6. Как это работает

### 6.1. Поток загрузки нового файла

```
Пользователь загружает файл в медиабиблиотеку
        ↓
WordPress создаёт attachment + thumbnail/medium/large
        ↓
Хук wp_update_attachment_metadata
        ↓
WebDAV_Storage_Offload::maybe_offload_metadata()
        ↓
Для каждого файла (оригинал + размеры):
  ├─ Проверить, что файла ещё нет в WebDAV
  ├─ PUT в WebDAV (curl streaming или wp_remote_request)
  ├─ PROPFIND: проверить, что файл реально создан
  └─ Если delete_local = true → удалить с диска
        ↓
Готово. Ссылка в контенте ведёт на public_url или /wp-json/...
```

### 6.2. Что выгружается

Для **изображения**:
- Оригинал: `2026/10/photo.jpg`
- Размеры: `2026/10/photo-150x150.jpg`, `photo-300x200.jpg` и т.д.

Для **PDF**: только оригинал.

### 6.3. Что НЕ выгружается

- Файлы, которые ещё не дошли до `wp_update_attachment_metadata` (например, прерванная загрузка).
- Файлы, которые не удалось прочитать локально (нет прав).
- Файлы, которые **уже есть** в WebDAV (проверка через `PROPFIND`, `exists()`).

### 6.4. Создание папок

Если в WebDAV ещё нет папки `2026/10/` — плагин сделает `MKCOL` для каждого сегмента пути:

```
MKCOL 2026/
MKCOL 2026/10/
PUT   2026/10/photo.jpg
```

Если `MKCOL` вернул `405 Method Not Allowed` — значит, папка уже есть, плагин продолжает (это не ошибка).

### 6.5. Удаление файла

Хук `delete_attachment` → `maybe_delete_remote()`:
- Собирает все пути (оригинал + размеры) из `_wp_attachment_metadata`.
- Отправляет `DELETE` в WebDAV для каждого.
- Код `404` считается успехом (файла и так нет).

## 7. Публичный URL и REST-прокси

### 7.1. Если задан `public_url`

- WordPress-функция `wp_upload_dir()` возвращает `baseurl = public_url`.
- Все картинки в контенте, медиабиблиотеке и `get_the_post_thumbnail_url()` — ведут на `public_url`.
- Файл физически **лежит только в WebDAV** (если `delete_local = true`).
- Web-сервер **не** проксирует — браузер идёт напрямую в WebDAV.

**Плюсы:**
- Минимальная нагрузка на WordPress.
- Быстрая отдача файлов (особенно если WebDAV = CDN или Nextcloud с хорошим каналом).

**Минусы:**
- Нужен публичный доступ к WebDAV-папке (что не всегда возможно).

### 7.2. Если `public_url` пуст

- `upload_dir['baseurl']` = `/wp-json/webdav-storage/v1/file/...`.
- Все ссылки ведут на REST-прокси WordPress.
- Плагин сам стримит файл из WebDAV через curl, с кэшем и Range.

**Плюсы:**
- WebDAV может быть закрыт паролем / не иметь публичного доступа.
- Работает «из коробки».

**Минусы:**
- Каждая картинка = запрос PHP + запрос к WebDAV.
- Больше нагрузки на сервер WordPress.
- Медленнее отдача.

### 7.3. Как работает REST-прокси

**URL:** `GET /wp-json/webdav-storage/v1/file/<путь>`  
**Пример:** `GET /wp-json/webdav-storage/v1/file/2026/10/photo.jpg`

Что делает:
1. Декодирует percent-encoding (`%D0%BA` → `к`) — важно для кириллических имён.
2. Проверяет путь (не пускает `..`, абсолютные пути).
3. Открывает `GET` к WebDAV с заголовками `If-None-Match`, `If-Modified-Since`, `Range`.
4. Проксирует ответ (статус, Content-Type, Content-Length, ETag, Last-Modified) браузеру.
5. Кэширует: `Cache-Control: public, max-age=2592000, immutable` (30 дней).

**Поддержка видео:** работает `Range` → видео можно перематывать.

**При ошибке:** возвращает `404` (не `502`), чтобы браузер не «залипал» на битом соединении.

## 8. Пакетная выгрузка существующих файлов

### 8.1. Как запустить

**Настройки → WebDAV Storage → Существующие медиафайлы → «Выгрузить существующие медиафайлы в WebDAV»**.

### 8.2. Что произойдёт

1. JS читает все attachments из БД **по одному** (по ID).
2. На каждый файл отправляет AJAX `webdav_offload_batch`.
3. Плагин:
   - Берёт метаданные attachment.
   - Выгружает оригинал + размеры.
   - Возвращает `{ done: false, offset: N+1 }`.
4. JS повторяет, пока `done: false` не станет `true`.
5. Показывает прогресс-бар, счётчик, ошибки.

### 8.3. Сколько времени занимает

- **100 файлов** — ~2–5 минут при нормальном канале.
- **1000 файлов** — 20–60 минут.
- **10 000 файлов** — несколько часов.

**Важно:** процесс **не прерывается** закрытием браузера — можно оставить вкладку открытой и уйти. Но **если** браузер закроется, процесс **остановится** (JS перестанет отправлять новые AJAX). В этом случае можно запустить заново — плагин **пропускает** файлы, которые уже есть в WebDAV (`SKIP: File already exists`).

### 8.4. Ошибки на конкретном файле

- Плагин **не останавливается** на ошибке, а идёт дальше.
- В прогресс-баре будет счётчик ошибок.
- В лог-файл (если включён `debug_mode`) пишется причина.
- Пропущенные файлы можно догрузить повторным запуском (они будут обработаны заново).

### 8.5. Пропуск уже выгруженных

При каждом `PUT` предварительно вызывается `exists()` (PROPFIND). Если файл уже есть — не загружается повторно, а считается «успешным». Это защищает от повторной загрузки при перезапуске.

## 9. Удаление локальных файлов

### 9.1. Когда включать

Только **после**:
1. Успешной проверки «Проверить подключение».
2. Успешной тестовой загрузки 1–2 файлов.
3. Проверки, что файлы реально в WebDAV.
4. Бэкапа `wp-content/uploads/` (на всякий случай).

### 9.2. Что удаляется

- Оригинал (`2026/10/photo.jpg`).
- Все размеры (`photo-150x150.jpg`, `photo-300x200.jpg` и т.д.).
- **Не удаляются:** сами записи attachment в БД, метаданные, ссылки в контенте.

### 9.3. Что произойдёт после удаления

- Ссылки в контенте продолжат работать:
  - Если `public_url` задан — браузер идёт напрямую в WebDAV.
  - Если `public_url` пуст — работает REST-прокси.
- **Медиабиблиотека** покажет иконки, но превью может быть «битым», если плагин не подменяет URL. На практике WordPress использует `wp_get_attachment_image_src()`, который возвращает URL на основе `upload_dir['baseurl']` — так что всё работает.

### 9.4. Как отключить удаление

- Снять галочку **«Удаление локальных файлов»** → Сохранить.
- Уже удалённые файлы не вернутся. Восстановление — из WebDAV-копии через `rclone` / `wget`.

## 10. Уникальные имена файлов

### 10.1. Логика

Перед `PUT` плагин проверяет, есть ли файл в WebDAV. Если да — пробует `name-1.ext`, `name-2.ext`… до `name-99.ext`. Если все заняты — оставляет исходное (перезапишет).

### 10.2. Когда отключать

- Если в WebDAV-папке **гарантированно** нет коллизий (UUID-имена, хэши).
- Если нужно **обновлять** файлы с тем же именем (перезапись) — но это опасно для старых ссылок.

### 10.3. Совместимость с кириллицей

Плагин использует `preg_match('/^(.*?)(\.[^.]+)$/u', ...)` вместо `pathinfo()` — чтобы **не терять кириллицу** в именах файлов (`фото.jpg` → `фото-1.jpg`, а не `-1.jpg`).

## 11. Логирование и отладка

### 11.1. Включение

**Настройки → WebDAV Storage → Режим отладки → Сохранить**.

### 11.2. Где лог

```
/wp-content/uploads/webdav-offload-debug.log
```

### 11.3. Как скачать

В админке, рядом с чекбоксом «Режим отладки», появляются кнопки:
- **Скачать лог** — открывает файл.
- **Очистить лог** — удаляет.

### 11.4. Формат строк

```
[2026-10-30 14:35:22] PUT attempt 1 failed (HTTP 423: ) Retrying in 1s... {"path":"2026/10/photo.jpg"}
[2026-10-30 14:35:24] SKIP: File already exists in WebDAV {"path":"2026/10/photo-150x150.jpg"}
[2026-10-30 14:35:25] ERROR: Failed to upload 2026/10/photo.jpg: PUT failed: HTTP 507. cURL error:
```

### 11.5. Что логируется

- Все попытки `PUT`, `MKCOL`, `DELETE`, `PROPFIND` при ошибках.
- SKIP-файлы (уже есть в WebDAV).
- Ошибки сети, HTTP-коды, ошибки curl.
- Только если `debug_mode = true` — пишется в файл; **всегда** пишется в `error_log` PHP (можно смотреть через `debug.log`, если включён `WP_DEBUG_LOG`).

### 11.6. Ротация

Лог **не ротируется** автоматически. Если он вырос >10MB — скачайте и очистите вручную.

## 12. Обработка ошибок

### 12.1. Последние ошибки в админке

На странице **Настройки → WebDAV Storage** вверху — блок «Последние ошибки WebDAV» (до 20 записей). Хранятся в `wp_options` (`webdav_storage_recent_errors`).

Также — всплывающее уведомление в админке, если ошибка была за последние 5 минут.

### 12.2. Типы ошибок

| HTTP | Что означает | Что делать |
|---|---|---|
| **401** | Неверный логин/пароль | Проверить настройки |
| **403** | Нет прав на запись | Проверить права в WebDAV |
| **404** | Папка не существует и не создаётся | Создать папку вручную |
| **405** | `MKCOL` на существующую папку | Не ошибка, плагин продолжает |
| **409** | Конфликт (папка не создана) | Создать родительские папки вручную |
| **423** | Locked | Повтор через 1–2 сек (плагин делает автоматически, до 3 попыток) |
| **507** | Нет места на диске | Очистить WebDAV |
| **0** | Сетевая ошибка / таймаут | Проверить доступность WebDAV |

### 12.3. Что не блокирует загрузку

Плагин **не блокирует** загрузку файла через медиабиблиотеку, если WebDAV недоступен. Файл останется локально, ошибка попадёт в лог. Это значит:

- Пользователь не увидит ошибку на фронтенде.
- При следующей попытке (повторная загрузка или пакетная) файл будет выгружен.

### 12.4. Плагин не работает, если WebDAV недоступен?

- Если `enabled = true` и WebDAV **полностью** лёг — новые загрузки **всё равно пройдут** (сохранятся локально), но в WebDAV не попадут.
- Ссылки будут работать **локально** (файл-то есть).
- При следующем запуске пакетной выгрузки — уйдут.

## 13. Миграция на production

### 13.1. Перенос плагина

Через FTP: скопировать `/wp-content/plugins/webdav-storage-offload/` с dev на prod. Активировать.

### 13.2. Перенос настроек

**Вариант А — вручную:**

Открыть **Настройки → WebDAV Storage** на dev → переписать все значения → ввести на prod.

**Вариант Б — через БД:**

```sql
SELECT option_value FROM wp_options WHERE option_name = 'webdav_storage_settings';
```

Скопировать значение, вставить на prod:

```sql
UPDATE wp_options SET option_value = '...' WHERE option_name = 'webdav_storage_settings';
```

⚠️ **Пароль** зашифрован ключом `wp_salt('auth')`. Если на prod **другой** `AUTH_KEY` в `wp-config.php` — пароль **не расшифруется**. В этом случае нужно **ввести пароль заново** через админку.

**Вариант В — через WP-CLI:**

```bash
# На dev
wp option get webdav_storage_settings --format=json > webdav.json

# На prod
wp option update webdav_storage_settings "$(cat webdav.json)" --format=json
```

Тот же нюанс с паролем.

### 13.3. Перенос медиафайлов

**Если `delete_local = false` на dev** — файлы лежат в `/wp-content/uploads/`, переносятся как обычно (rsync / FTP / архив).

**Если `delete_local = true` на dev** — локальных копий нет. Варианты:

**A. Скачать с WebDAV обратно:**

```bash
rclone copy webdav:/wordpress /path/to/prod/wp-content/uploads/ -P
```

**B. Не переносить файлы, а скопировать WebDAV-папку:**

Если WebDAV на dev и prod — **один и тот же**, ничего делать не нужно — плагин на prod будет читать оттуда же.

**C. Переключить prod на тот же WebDAV-аккаунт:**

Достаточно указать тот же `url` и логин/пароль.

### 13.4. Переключение URL

После переноса:

1. **Настройки → WebDAV Storage** → проверить `url`, `public_url`.
2. Убедиться, что `public_url` указывает на **prod**-версию (или общий CDN).
3. Нажать **«Проверить подключение»**.
4. **Сохранить**.

### 13.5. Что проверить

- [ ] Плагин активен.
- [ ] URL, логин, пароль корректны.
- [ ] «Проверить подключение» → ✓.
- [ ] Загрузить тестовую картинку → появилась в WebDAV.
- [ ] Ссылка на картинку в контенте открывается.
- [ ] Если `public_url` пуст — REST-прокси работает (`/wp-json/webdav-storage/v1/file/...`).
- [ ] Если `public_url` задан — прямая ссылка открывается.
- [ ] Старые файлы доступны (из WebDAV или локально).

### 13.6. Правила `.htaccess` для REST-прокси

Обычно ничего не нужно, но если у вас **агрессивные правила безопасности** (например, запрет `*.jpg` через `.htaccess`), REST-прокси может не работать. Проверить:

```apache
# Должно работать:
/wp-json/webdav-storage/v1/file/*
```

Если не работает — добавить исключение:

```apache
<IfModule mod_rewrite.c>
RewriteCond %{REQUEST_URI} ^/wp-json/webdav-storage/
RewriteRule .* - [L]
</IfModule>
```

### 13.7. Кэш и CDN

Если перед сайтом стоит **Cloudflare / Nginx Cache / Varnish**:

- REST-прокси отдаёт файлы с `Cache-Control: public, max-age=2592000, immutable` — CDN закэширует на 30 дней.
- Если файл в WebDAV **изменился** с тем же именем — кэш не обновится. Используйте **уникальные имена** (плагин это делает по умолчанию) или **purge** кэша вручную.

## 15. Диагностика проблем

### 15.1. Новые файлы не выгружаются

1. **Настройки → WebDAV Storage** — галка **«Включить выгрузку»** стоит?
2. **`url`** заполнен?
3. **`debug_mode`** → включить, загрузить тестовый файл, скачать лог:
   ```
   grep "PUT" webdav-offload-debug.log
   ```
4. **F12 → Network** при загрузке через медиабиблиотеку — есть ошибки?

### 15.2. Пакетная выгрузка «зависает»

- Открыть **F12 → Console** — есть ошибки JS?
- **F12 → Network** — AJAX `webdav_offload_batch` → смотреть ответ.
- Если `500` — открыть `wp-content/debug.log` (нужен `WP_DEBUG_LOG = true`).
- Если таймаут — уменьшить размер батча (сейчас 1 файл за запрос) — уже минимум.

### 15.3. «Не удалось создать тестовый файл. HTTP 401»

- Логин/пароль неверные.
- Basic Auth отключён на сервере — проверьте настройки WebDAV.
- Для Nextcloud — используйте **app password**, а не основной.

### 15.4. «Не удалось создать тестовый файл. HTTP 403»

- У пользователя нет прав **на запись** в указанную папку.
- Проверить права в WebDAV-клиенте.

### 15.5. «Не удалось создать тестовый файл. HTTP 404»

- Папка из `url` **не существует** и не может быть создана (родительская папка недоступна).
- Создать папку вручную через WebDAV-клиент.

### 15.6. «Не удалось создать тестовый файл. HTTP 507»

- На WebDAV-сервере **закончилось место**. Очистить.

### 15.7. Файл выгружается, но картинка на сайте не открывается

- Если `public_url` задан — открыть его в браузере напрямую, проверить, что файл доступен.
- Если `public_url` пуст — открыть `/wp-json/webdav-storage/v1/file/2026/10/photo.jpg`. Если 404 — плагин не может достучаться до WebDAV. Проверить `debug_mode` + лог.
- **F12 → Console** — какая ошибка?

### 15.8. REST-прокси возвращает 404, но файл в WebDAV есть

- **Кириллица в имени:** `фото.jpg` → браузер отправляет `%D1%84%D0%BE%D1%82%D0%BE.jpg`. Плагин должен декодировать (`rawurldecode`). Проверить, что версия плагина ≥ 1.4.1 (в ней исправление).
- **Trailing slash:** `/2026/10/photo.jpg/` — не работает. Проверить, что URL без слэша в конце.
- **Nginx / .htaccess блокирует** `/wp-json/...` — см. [раздел 13.6](#136-правила-htaccess-для-rest-прокси).

### 15.9. REST-прокси отдаёт 502 / 504

- Таймаут к WebDAV. Увеличить:
  - `CURLOPT_TIMEOUT` в `curl_stream()` (сейчас 60 сек).
  - `CURLOPT_CONNECTTIMEOUT` (сейчас 10 сек).
- Или — использовать `public_url` напрямую.

### 15.10. Файл выгружен, но `delete_local` не удаляет

- Проверить, что **все** размеры успешно загрузились. Если хоть один `PUT` упал — `delete_local` не сработает (защита от потери).
- Смотреть лог: `all_ok` должен быть `true`.

### 15.11. Пароль не расшифровывается после переноса

**Причина:** на новом сервере другой `AUTH_KEY` в `wp-config.php`.

**Решение:**

1. Открыть **Настройки → WebDAV Storage**.
2. Ввести пароль заново.
3. Сохранить.

Или синхронизировать `AUTH_KEY` между dev и prod (не рекомендуется по соображениям безопасности).

### 15.12. Плагин ломает загрузку файлов (белый экран при upload)

- Проверить `wp-content/debug.log`.
- Скорее всего, нет `curl` и `file_get_contents()` не может прочитать большой файл (память).
- Установить `curl` на сервере.
- Или увеличить `memory_limit` до 256MB+.

### 15.13. Медиабиблиотека показывает «битые» превью

- Если `delete_local = true` и `public_url` не задан — превью идёт через REST-прокси. Он работает, но медленнее.
- Проверить, что `/wp-json/webdav-storage/v1/file/...` открывается.
- Если нет — см. 15.8.

### 15.14. «Выгружено 0 файлов», хотя медиафайлы есть

- `enabled = false` — плагин неактивен.
- Или все файлы **уже** в WebDAV (`SKIP`) — тогда `offset` растёт, но ошибок нет.
- Проверить лог: `SKIP: File already exists`.

## 16. Безопасность

### 16.1. Хранение пароля

- Шифруется AES-256-CBC.
- Ключ = `substr(hash('sha256', wp_salt('auth')), 0, 32)`.
- IV — случайный, при каждом сохранении новый.
- **Формат в БД:** `ossl:<base64_iv>::<base64_cipher>`.

Если `openssl` недоступен — fallback на `b64:<base64_plain>` (⚠️ **не шифрование**, а просто кодирование). Если на сервере нет openssl — **включите**, это важно.

### 16.2. Права WebDAV-пользователя

Создайте **отдельного пользователя** WebDAV **только** для этого сайта, с правами **только** на папку `/wordpress/`. Не давайте доступ ко всему аккаунту.

### 16.3. `wp-config.php`

Убедитесь, что `AUTH_KEY`, `SECURE_AUTH_KEY` и т.д. — **уникальные** и **длинные** (>64 символа). Их можно сгенерировать на `https://api.wordpress.org/secret-key/1.1/salt/`.

### 16.4. SSL

- `sslverify = true` **всегда** на production.
- WebDAV-сервер должен иметь валидный сертификат.

### 16.5. Публичный URL

- Если `public_url` — **публичная** папка Nextcloud (share link), то **все файлы** доступны по прямой ссылке без авторизации. Это может быть нежелательно для конфиденциальных документов.
- Альтернатива: не задавать `public_url`, использовать REST-прокси (авторизация не требуется для публичных картинок, но URL — с вашего домена).

### 16.6. REST-прокси

- Открыт **без авторизации** (`permission_callback => '__return_true'`).
- Это **нормально** — картинки на сайте и так публичные.
- **Но** если в WebDAV есть **приватные** документы — их URL можно угадать (например, `/wp-json/webdav-storage/v1/file/private/contract.pdf`).
- **Не храните** приватные файлы в той же папке, что и публичные.

## 17. Известные ограничения

1. **Не выгружает файлы, загруженные до активации плагина** — для них нужна **пакетная выгрузка**.
2. **Не синхронизирует обратно** — если файл удалён в WebDAV, на сайте будет 404 (если `public_url` задан) или REST-прокси вернёт 404.
3. **Пароль не переносится** между серверами с разным `AUTH_KEY` — ввести заново.
4. **Лог не ротируется** — чистить вручную.
5. **Нет хуков** для разработчиков — всё «жёстко» в классе. Кастомизация — через фильтр `upload_dir` (уже используется) или прямой правкой.
6. **При очень больших файлах** (>500MB) может не хватить `memory_limit` при `file_get_contents()`. Решение: **curl streaming** (плагин использует автоматически, если curl есть).
7. **REST-прокси не кэшируется** на уровне WordPress (только браузер/CDN). Для продакшена лучше `public_url`.

## 18. Отключение и удаление

### 18.1. Временное отключение

**Настройки → WebDAV Storage → снять «Включить выгрузку» → Сохранить.**

- Новые файлы **не выгружаются**.
- Существующие ссылки **работают** (файлы либо локально, либо в WebDAV).
- Пакетная выгрузка **не запускается**.

### 18.2. Полное отключение

**Плагины → WebDAV Storage Offload → Деактивировать.**

- CPT, настройки, лог — **остаются** в БД.
- Ссылки на файлы **продолжают работать** (WordPress не проверяет, активен ли плагин — просто отдаёт URL).

### 18.3. Удаление

**Плагины → WebDAV Storage Offload → Удалить.**

При удалении (через `register_uninstall_hook`):

- Удаляется `wp_options['webdav_storage_settings']`.
- Удаляется `wp_options['webdav_storage_recent_errors']`.
- **Лог-файл НЕ удаляется** — удалить вручную:
  ```
  /wp-content/uploads/webdav-offload-debug.log
  ```

**Медиафайлы в WebDAV не трогаются.** Если они были выгружены с `delete_local = true` — локальных копий нет. После удаления плагина ссылки на сайте **сломаются** (REST-прокси исчезнет, `public_url` вернётся к стандартному `/wp-content/uploads/`, где файлов нет).

### 18.4. Как «вернуть всё назад»

Если нужно **скачать файлы из WebDAV обратно**:

```bash
rclone copy webdav:/wordpress /path/to/wp-content/uploads/ -P
```

Или через WebDAV-клиент (Nextcloud desktop, Cyberduck, WinSCP).

После этого — деактивировать / удалить плагин.
